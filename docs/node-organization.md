# 从 Gist 生态看：节点到底该怎么整理

> 语料：2026-11-23 对 `gist.github.com/search?q=clash&s=updated` 一类搜索做的一次快照。
> 214 个可读 gist → 57 个"像节点源"的 → 46 个实际抓取 → 14,026 条节点记录（13,988 条成功归一）。
> 所有数字都可以用 `tools/` 里的脚本重跑，明细见 [feeds.md](feeds.md)。

---

## 0. 结论先行

1. **生态早就把"节点"和"订阅"拆开了**。主流发布形态是三件套：`all.yaml`（纯节点）+ `base64.txt`（跨客户端传输）+ `mihomo.yaml`（带分组的成品配置）。节点是数据，分组和规则是视图。
2. **命名是事实标准，但不是 ID**。`🇭🇰HK_1|8.4MB/s|YT-HK|GPT⁺-TW` 这种五段式被 18/46 个源完整采用；但同一节点在两轮更新里有 **55% 的概率被改名**（速度、健康度刷新），拿名字当唯一键必然重复计数。
3. **必须用"传输指纹"去重**：除 `name` 外的全部字段。同源内重复率 3.4%，跨源重复率仅 5.8% —— 跨源不是大量重复，而是**长尾**。
4. **源的边际收益极陡**：贪心选源，**3 个源覆盖 50%，5 个覆盖 80%，11 个才到 95%**。堆 40 个源不如精选 5 个大的 + 若干轮换池。
5. **池子换血极快**：相邻两版（≥24h 间隔）节点存活率中位数 **20%**，52% 的源低于 20%。这不是"收录一次用一年"的数据，而是需要滚动复测的流。
6. **`base64.txt` 是有损的**：21 个同时发布 trio 的源里，只有 5 个能完整表达。累计丢掉 851 个 `http`、60 个 `socks5`（URI 语法里没有它们的通用形式）。只拿 base64 当唯一来源 = 静默丢掉约 1/4 的节点。
7. **发布者自己也不筛质量**：带 `健康度%` 的 3,090 个节点里，**47% 是 0%**，73% 低于 20%。`history.yaml` 这类"历史池"更是把死节点全留着。整理的第一价值不是"多"，是**筛**。

## 1. 怎么采到的（方法可复现）

| 环节 | 办法 | 坑 |
|---|---|---|
| 发现 | `gist.github.com/search?o=desc&s=updated&q=<kw>&p=N` | 免登录每页固定 10 条，且 **`page=` 无效、必须用 `p=`**；不登录翻不了深页 |
| 元数据 | `GET /gists/{id}`（`api.github.com`） | 这个域名**直连可用**，走代理反而更慢（0.5s vs 6.7s）；`/gists/{user}/{id}` 路径 404 |
| 内容 | 同上响应里的 `files[*].content` | 单文件 1MB 截断，`history.yaml` 会被截 |
| 历史 | `GET /gists/{id}/commits?per_page=100` | 默认只回 30 条，不显式 `per_page` 会把"更新了 300 次"误判成 30 次 |
| 网页 | `gist.github.com` | 这个域名在本地**必须走代理**，直连 21s 超时 |

10 个查询词（`clash` `mihomo` `sing-box` `v2ray` `订阅` `subs-check` `hysteria2` `all.yaml` `base64.txt` `机场`）× 3 页 → 215 个候选，去重后 214 个。按"文件名像节点源 or 描述是 `Configuration`"过滤 → 57 个，实际抓到 46 个。

> 顺带一个筛选经验：搜索结果的**描述**几乎无用（`Configuration` 占 25/214，空占 35/214），真正有信息的是**文件名组合**。

## 2. 发布形态：三件套 + 两个附件

46 个源里，节点的载体分布：

| 文件 | 出现次数 | 含义 | 特征 |
|---|---:|---|---|
| `all.yaml` | 25 | 纯 `proxies:` 列表 | 最干净的"节点数据"层 |
| `base64.txt` | 25 | 同一批节点的 URI 编码 | 跨客户端；**有损**（见 §2.2） |
| `mihomo.yaml` | 21 | 节点 + 分组 + 规则 | 拿来即用的成品 |
| `history.yaml` | 5 | "历史池" | 只增不减，含大量 0% 死节点 |
| `sub` | 2 | 占位符 | 内容写着 `subs-check-pro subscription sync placeholder`，暴露了生成器 |

### 2.1 生成器：subs-check 家族

`sub` 占位符 + 节点名里的 `|X|sinspired/subs-check` 直接指向 [beck-8/subs-check](https://github.com/beck-8/subs-check) 和它的 PRO 分支 [sinspired/subs-check-pro](https://github.com/sinspired/subs-check-pro)。官方管线（README 架构图）就是标准答案：

```
订阅链接 → 转 YAML → 节点去重 → 测活 → 流媒体检测+重命名 → filter → 测速
        → all.yaml → sub-store 转 mihomo.yaml / base64.txt → 上传 Gist/R2/WebDAV/S3
```

也就是说：**"整理节点"在生态里= 一条带 5 道闸的流水线**，不是手工归类的活。区别只在于每道闸的参数。

### 2.2 base64 的有损点（实测）

| 协议 | 21 个 trio 源累计丢失 |
|---|---:|
| `http` | 851 |
| `socks5` | 60 |
| `hysteria2` | 3 |
| `ss` / `vless` / `vmess` / `trojan` / `anytls` / `wireguard` / `hysteria` / `ssr` | 0 |

原因很直接：`ss/vmess/vless/trojan/hysteria2/anytls` 都有 URI 规范，`http`/`socks5` 没有。但 `http` 恰恰是免费池里最常见的协议（本语料 2,749 条，占 20%）——**用 base64 当唯一入口，等于把公共 HTTP 代理全部静默丢弃**。

### 2.3 分组模板只有两款

21 个带 `mihomo.yaml` 的源，`proxy-groups` / `rules` 数量：

| 模板 | 源数 | 说明 |
|---|---:|---|
| 10 / 17 | 10 | 精简版：1 主选择 + 3 地区 + 少量服务组 + 基础分流 |
| 29 / 34 | 8 | ACL4SSR 全量版（含 `📲 电报消息` `💬 Ai平台` `🎥 奈飞视频` … 7 个地区 `url-test`） |
| 32 / 37 | 2 | 上面那款 + 3 个自定义组 |
| 44 / 38 | 1 | 臃肿到 44 组，反例 |

全部 21 个的 `rule-providers` 都指向 `testingcf.jsdelivr.net/gh/ACL4SSR/ACL4SSR@master/...`（2 个额外挂了 `cdn.jsdelivr.net` 做备份）。**规则是第三方资产，不要自己维护**。

## 3. 命名 ABI：最有价值的一层

### 3.1 事实标准（五段式）

```
🇭🇰HK_1     | 8.4MB/s | 92% | TK-SG    | YT-HK | GPT⁺-TW | GM-US
└ 地区+序号 └ 下载速度 └ 存活率 └ 落地/线路 └ 各平台解锁区域（可多段）
```

- 地区：国旗 emoji + ISO2，可选上标 `²`（多入口标记）
- 速度：`MB/s` 或 `KB/s`（两种单位混用，归一时要 `/1024`）
- 存活率：1–3 位百分比，`0%` 表示测活失败但仍被保留
- 线路：`TK-GCP` `R002-260618`（`260618` 是**到期日 2026-06-18**，不是 ID）
- 解锁：`YT`(YouTube) `NF`(Netflix) `GPT⁺` `GM`(Gemini) `D+`(Disney) `X`(Twitter) `TK`(TikTok)

### 3.2 三种流派并存

13,988 条节点按"地区怎么写"统计：

| 流派 | 占比 | 例子 |
|---|---:|---|
| 国旗 + ISO2/ISO3 | 73.7% | `🇭🇰HK_1\|8.4MB/s`、`🇲🇾 MYS-4G` |
| 中文城市/机位名 | 14.7% | `坚果-香港`、`未知 (PuddinCat)-1` |
| 无标签 | 11.6% | `EUR-FREE-5D`、`🔥Join+Telegram:@xxx`、`🏴‍☠_1🏴‍☠_13103.177.177.250:8080-02` |

字段覆盖率：带速度 **40.2%**，管道分隔 **62.6%**，带解锁标签 **20.2%**。按源看，18/46 完整采用五段式，8 个部分采用，20 个基本不用。

### 3.3 所以：名字只能当"展示 + 遥测"

名字里混进了三类破坏身份的东西：

1. **会变的遥测**：速度、健康度（同一节点 55% 概率在两轮间改名）
2. **会过期的一次性信息**：`R002-260618`（到期日）、广告 `🔥Join+Telegram:@xxx`
3. **重复/冲突**：`🏴‍☠_1🏴‍☠_13103.177.177.250:8080-02` 把 host:port 塞进名字

> 结论：解析名字 → 得到结构化元数据（地区/速度/健康/解锁/线路/到期），然后**把名字丢掉重写**。这一步是整理的核心，不是可选项。

## 4. 身份与去重

### 4.1 传输指纹（transport fingerprint）

同一个节点 = 除展示字段外，所有字段完全一致。

```python
COSMETIC = {"name", "udp", "client-fingerprint", "skip-cert-verify",
            "fingerprint", "tfo", "mptcp", "xudp", "packet-encoding"}
fp = sha1(json.dumps({k: v for k, v in proxy.items() if k not in COSMETIC},
                     sort_keys=True)).hexdigest()[:16]
```

为什么不是 `(type, server, port)`：实测 973 个节点里有 **106 个 `server:port` 被多个节点共用**（最高一个 IP:443 上挂了 22 个节点）——这是多用户入口/中转前门，按 host:port 去重会误杀 186 个真实节点。

为什么不是"名字"：见 §3.3。

### 4.2 实测重复率

| 口径 | 数值 |
|---|---:|
| 单源内重复（14,026 → 去重后） | **3.4%** |
| 跨源重复（12,413 全局唯一 / 13,174 各源唯一之和） | **5.8%** |
| 出现在 2 个源的指纹 | 413 |
| 出现在 ≥3 个源的指纹 | 136 |

也就是说：**上游发布者基本已经自己去过重了**，你在汇聚层做的主要不是"消重"，而是"验证 + 归一 + 排名"。

### 4.3 同源池识别（谁在抄谁）

按 Jaccard 做两两比较，有三对源几乎完全同池：

```
xiaopicheng0414 ∩ suhuicao1-arch   jaccard 1.00  (10 节点)
xiaopicheng0414 ∩ antioxi1         jaccard 0.91
suhuicao1-arch  ∩ antioxi1         jaccard 0.91
```

这不是"巧合"，是同一个上游（或同一份 whitelist）被多个账号转手。**选源时要按池子去重，不是按账号去重**，否则你以为有 3 个源，其实只有 1 个。

## 5. 质量信号：怎么筛

### 5.1 发布者给的信号（可用但不可信）

| 信号 | 样本 | 分布 |
|---|---:|---|
| 健康度 `\|N%\|` | 3,090 条 | 0%：**47%**；<20%：**73%**；≥60%：5% |
| 速度 `\|N MB/s\|` | ~40% 节点 | p10 = 0.6，中位 2.8，p90 = 8.0 MB/s |

**结论**：`0%` 的节点不会被发布者剔除（`history.yaml` 甚至是"只增不减"），所以"收录"≠"可用"。筛选闸必须自己设。

### 5.2 自己测的信号（必须补）

发布者给不出、但对"整理"最关键的四个：

1. **真实存活**（TCP 握手 + 一次 204 请求），而不是历史百分比
2. **可用速度**（下载 10MB 或 5s 限时吞吐）
3. **地区**：名字只覆盖 ~90%，剩下靠 IP GeoIP。好消息是 **67% 的 server 是 IP 字面量**，可以直接批量 GeoIP；33% 是域名，需要先解析
4. **ASN/机房**：`GCP` `AWS` `TK` 这类"线路"标签只出现在名字里，不可靠；ASN 能反推真实落地（云厂商 IP 段 vs 家宽）

### 5.3 实测：静态清单里只有约一半是活的（2026-11-23，Azure runner）

`tools/probe.py` 在 CI 里对 800 条做了一次真实探测：

| 阶段 | 结果 |
|---|---|
| 静态门限后 | 7,815 条 |
| TCP 可达 | 577 / 800（**72%**） |
| 协议层延迟测试通过（mihomo 真实握手） | 379 / 577（**66%**） |
| **真正可用** | **379 / 800（47%）** |
| 延迟中位 / 吞吐中位 | **325 ms / 3.7 MB/s**（p90 8.4） |
| GeoIP 补齐地区 | 67 / 800（名字里没有地区标签的那批） |

结论：发布者的“已测速/已测活”标签**大约有一半不可信**；而实测速度中位（3.7 MB/s）比发布者自报（2.8 MB/s）还高——因为自报值往往来自更早的轮次。

### 5.4 协议白/黑名单

本语料协议构成（去重后 9,826 条）：

| 协议 | 数量 | 建议 |
|---|---:|---|
| vless | 4,354 | 保留（含 18% REALITY） |
| anytls | 2,588 | 保留（新兴，稳定性待观察） |
| ss | 986 | 保留 |
| hysteria2 | 737 | 保留 |
| trojan | 638 | 保留 |
| vmess | 445 | 保留 |
| hysteria / ssr / tuic / wireguard / mieru | 77 | 按客户端能力取舍 |
| **http / socks5** | **2,749 / 682** | **默认丢弃**：公共代理，任何人可用、寿命以小时计、无 TLS |

`http`+`socks5` 占原始语料的 **26%**，但它们同时也是最不稳定的部分——直接黑名单能一口气砍掉四分之一的噪声。

## 6. 归一：地区、单位、标签

三个必须做的归一化：

| 维度 | 输入样式 | 归一动作 |
|---|---|---|
| 地区 | `🇭🇰HK` / `HKG` / `香港` / `[hk]` | 别名表 → ISO2；失败则 GeoIP(server) 兜底；再失败归 `??` |
| 速度 | `8.4MB/s` / `168KB/s` | 统一 MB/s（KB ÷ 1024）；缺失记为 `None`，不要填 0 |
| 解锁 | `GPT⁺` `GM⁻` `NF` `X` `D+` `YT-HK` | 词表映射到 `chatgpt/gemini/netflix/twitter/disney/youtube`，`-XX` 后缀是**落地地区**不是解锁状态 |

归一后地区分布（9,826 条）：

```
US 2203 · DE 1046 · ?? 918 · HK 876 · JP 679 · SG 635 · NL 535 · GB 337
TW 319 · FR 258 · MY 239 · RU 225 · IT 189 · CA 170 · …
```

`??` 从 66%（只按国旗解析）降到 **9.3%**——多流派解析 + 中文别名的收益就在这里。

## 7. 分层：节点 / 分组 / 规则

生态里成熟的结构是三层解耦，抄这个结构就行：

| 层 | 内容 | 变化频率 | 谁维护 |
|---|---|---|---|
| L1 节点 | `proxies: [...]` | 每分钟 | 采集器 |
| L2 分组 | `proxy-groups` | 每周 | 模板（10 组或 29 组二选一） |
| L3 规则 | `rules` + `rule-providers` | 每月 | ACL4SSR / 第三方 list |

29 组模板的实际构成（可当 checklist）：

- 1 个总选择 `🚀 节点选择`（默认指向 `♻️ 自动选择`）
- 1 个 `♻️ 自动选择`（`url-test`，`interval: 300`，`tolerance: 50`）
- 20 个服务组：`📲 电报消息` `💬 Ai平台` `📹 油管视频` `🎥 奈飞视频` `📺 巴哈姆特` `📺 哔哩哔哩` `🌍 国外媒体` `🌏 国内媒体` `📢 谷歌FCM` `Ⓜ️ 微软Bing/云盘/服务` `🍎 苹果服务` `🎮 游戏平台` `🎶 网易音乐` `🎯 全球直连` `🛑 广告拦截` `🍃 应用净化` `🐟 漏网之鱼`
- 7 个地区组：`🇭🇰 香港节点` `🇯🇵 日本节点` `🇺🇲 美国节点` `🇨🇳 台湾节点` `🇸🇬 狮城节点` `🇰🇷 韩国节点` + `🎥 奈飞节点`

**关键设计点**：地区组是 `url-test`（自动选最快），服务组是 `select`（人工指定策略）——"按地区"是节点属性，"按应用"是使用策略，两者不要混在一个维度里。

## 8. 选源：边际收益与生命周期

### 8.1 覆盖曲线（40 个可比源，12,413 个唯一节点）

| 选源数 | 1 | 2 | 3 | 4 | 5 | 8 | 11 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 覆盖 | 28% | 49% | 66% | 79% | 86%* | 93% | 95% |

\* 精确值：3 → 50%，5 → 80%，11 → 95%。前 5 名依次是 `HAIDEJIANG`(3482)、`itq5`(2539)、`Hadithub`(2170)、`yockliu`(1577)、`rockdale1899-alt`(973)。

### 8.2 更新频率与存活

| 指标 | 值 |
|---|---|
| 更新间隔中位数 | **10.2 分钟**（p90 = 9 小时，说明有 1/10 的源基本停更） |
| 24h 节点存活中位数 | **20%**（均值 39.5%） |
| 存活率 ≤20% 的源 | 52.3% |
| 存活率 ≥80% 的源 | 27.3% |

极端例子：`Tdison` 日存活 4%，`kenzhao11` / `tyoung-code` 0%（整池轮换）；而 `HAIDEJIANG` 99%、`dalazhi` 100%（池子几乎不变，但里面 47% 是 0% 死节点）。

**两种源要分开对待**：
- **稳定大池**（存活高、换血慢）：适合当主力，但要自己复测，因为里面混着历史死节点
- **轮换池**（存活低、整池替换）：适合当补充，必须高频重测，否则你拿到的是一堆昨天的 IP

## 9. 推荐的整理流水线

```
L0 采集    源清单（按池去重）→ 抓取 → 带 source_id + fetched_at 落库
L1 解析    name → {region, speed, health, expiry, unlock[], line}
L2 身份    transport fingerprint（除 name 外全字段）→ 去重，保留最好元数据
L3 验证    TCP 握手 + 204 → GeoIP(ASN/国家) → 吞吐 → 解锁探测
L4 筛选    协议白名单 + 存活 + 速度门限 + ASN 黑名单
L5 发布    重命名（规范 ABI）→ 地区/服务分组 → 输出 all.yaml / mihomo.yaml / base64(带损警告)
```

### 9.1 节点记录 schema（建议）

```jsonc
{
  "id": "a1b2c3d4e5f6",          // transport fingerprint
  "type": "vless", "server": "1.2.3.4", "port": 443,
  "params": { "...": "协议原始字段，原样保存" },

  "region": "HK",                 // 归一后的 ISO2，未知为 null
  "region_source": "name|geoip",  // 这个值是从哪来的（可审计）
  "asn": 45102, "org": "Alibaba", // GeoIP/ASN 结果
  "unlock": ["chatgpt", "youtube"], "unlock_regions": {"youtube": "TW"},

  "speed_mbps": 8.4, "latency_ms": 132, "alive": true,
  "measured_at": "2026-11-23T09:50:00Z", "probe": "tcp204",

  "sources": [{"owner": "Tdison", "gist": "6b7456…", "seen_at": "2026-11-23T09:19:49Z",
               "name_in_source": "🇭🇰HK_1|8.4MB/s|YT-HK|GPT⁺-TW"}],
  "first_seen": "2026-08-05", "miss_count": 0   // 连续缺席轮数 → 淘汰依据
}
```

要点：**原始字段与派生字段分开**（`params` vs 顶层），**每个派生值带来源**（`region_source`），**每次出现都记来源**（`sources[]`，用于识别同源池与生命周期）。

### 9.2 建议门限（基于本语料分布）

| 闸门 | 阈值 | 依据 |
|---|---|---|
| 协议 | 丢弃 `http` / `socks5` / `null` | 占语料 26%，无 TLS、寿命短 |
| 存活 | 连续 2 轮探测失败 → 淘汰 | 24h 中位存活仅 20%，单轮误判率高 |
| 速度 | ≥ 1 MB/s（缺失则要求延迟 < 800ms） | 语料 p10 = 0.6，中位 2.8 |
| 健康度（若有） | ≥ 30% | 发布者给的 47% 是 0% |
| 单源占比 | 任一源不超过总量的 40% | 防止单点（`HAIDEJIANG` 一源就 3482 条） |
| 重命名 | `{flag}{ISO2}_{序号}\|{速度}\|{解锁}`，序号按地区内速度重排 | 与生态 ABI 兼容，客户端可直接阅读 |
| 复测节奏 | 大池 60 min，轮换池 15 min | 更新间隔中位 10.2 min，节奏要对齐 |
| 主动探测 | TCP 可达 + 协议延迟，任一失败即丢 | 实测通过率 47%（见 §5.3） |

跑一遍这套门限的效果（`python organize.py --health 30 --speed 1`）：

```
13,988 条 → 7,816 条
  -3,681  协议黑名单(http/socks5)
  -1,774  健康度 < 30%
    -278  速度 < 1 MB/s
    -439  重复指纹
速度中位 2.8 → 3.1 MB/s，p90 8.0 → 12.8 MB/s
```

注意：**只有约 40% 的节点带速度、22% 带健康度**，所以「缺失值放行」是刻意的——缺失不等于差，但必须在 L3 自己补测，否则门限只对一小部分节点生效。

## 10. 反模式清单（每条都有实测支撑）

| 反模式 | 后果 | 证据 |
|---|---|---|
| 拿 `name` 当唯一键 | 同一节点每轮重复入库 | 存活节点中 55% 换了名字 |
| 拿 `server:port` 当唯一键 | 误删多用户入口 | 106 组 host:port 共用（最多 22 节点/IP） |
| 只吃 `base64.txt` | 静默丢掉 HTTP/SOCKS | 21 个源累计丢 851 + 60 条 |
| 把 `history.yaml` 全量导入 | 引入大量 0% 死节点 | 带健康度的节点里 47% 是 0% |
| 按"发布者"选源不去重池子 | 以为 3 个源其实 1 个 | 3 对源 Jaccard ≥ 0.91 |
| 只按国旗解析地区 | 1/3 节点被标 `??` | 修正后 `??` 从 66% 降到 9.3% |
| 自己维护 rules | 维护成本爆炸且必然过期 | 21/21 源都用 ACL4SSR + jsdelivr |
| 把速度写进节点 `id` | 每次测速都产生"新节点" | 见第一行 |
| 一次收录长期使用 | 一周后大半不可用 | 24h 中位存活 20% |
| 只堆源不做筛选 | 数量涨、可用率不涨 | 5 个源已覆盖 80% 唯一节点 |

## 12. 局限

- 快照只有一天。存活率是"一版 vs 24h 前的版本"的集合运算，**不等于**真实可用率——真实可用率要靠自己探测（本仓库的 `organize.py` 不做主动探测，只做结构与质量信号归一）。
- 免登录只能看每个查询的前 N 页（`p=` 可翻，但深度受限），语料偏向"最近更新"的源，老源覆盖不足。
- GeoIP 未实测。`67% IP 字面量` 只是说明"可行"，没有真的跑 MaxMind/ip-api。
- 抓到的 `history.yaml` 被 API 截断在 1MB，`HAIDEJIANG` 那 3,482 条可能仍非全量。
